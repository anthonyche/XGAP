## 实现与验证的范围

- 固定输入携带同一题的语义程序和未指定源地址的全局 SELECT，没有答案或人工源
  分配。XGAP 根据冻结 schema 中的类型和必需属性分配 Match 片段，再按冻结估计
  选一个计划；外部方法收到原封不动的全局查询，自行规划源访问。
- 共用规范化评分支持 XGAP JSON 行和外部 SPARQL literal 行，沿用文本 ID、整数、
  金额三位小数约定，保留行顺序和重复。URI/语言标记/错误列类型不会被强行改成答案。
  原始结果封存后才读取独立 reference；失败对空答案也计零。
- 同一 source observer 统计 ASK/SELECT、请求路径/请求体/响应体字节，不混用
  XGAP logical bytes 和外部 HTTP payload。HTTP 头、TCP/TLS 字节仍不在这个口径内。
- 方法 worker 加 hosted-method 进程共同受采样 RSS 预算约束，数据库进程单独计量；
  采样 CPU/RSS 不冒充硬件精确峰值或严格 OS 限额。外层计时包含请求读取、worker
  启动/准备/执行/落盘、观察、恢复和终态封存，最后一份计量文件与独立评分单列。
- 异常时终止本 serving session 自有的方法及数据库进程组，记录恢复费用，并拒绝
  复用旧 session。下一题需要新 session；不能仅凭 worker 退出或代理队列为空就
  声称后台查询已经停止。未运行的 cell 必须保留，不能冒充该方法的实测失败或零耗时。

当前 schema router 明确限于无未决 hole、以 Match 为远端输入的程序。已有三个金融
家族覆盖该边界；不宣称所有 Traverse 或全世界语义都已支持。普通 NL 的 XGAP 链路
此前已验收，但**共享 NL 前端到外部全局查询的编译尚未实现**，不能把本轮 gold
固定语义输入当作 FedUP/FedX 的端到端自然语言结果。

## 为什么 FedX 金额放大不能成为优势结论

源图分别有 211 和 36 个 RDF triples，交集 **24 条**：8 条类型、8 条业务 ID、
8 条内部身份。这些是为分源编译放置的重复身份/类型信息，不是24笔独立交易。

读取已保存结果后，仅在本地对两图的**集合并集**做一次诊断查询，223条 triples
得到 66、9，与独立 reference 一致；FedX 已保存结果恰好均为预期的 **128 倍**。
该全局查询有七个可在两源重复匹配的类型/业务 ID 模式，重复匹配的组合与
`2^7 = 128` 放大相吻合。这说明现表示存在集合/重复行语义混淆；不需要重跑
baseline 才能确认源文件确实有重叠，也不能直接把它归为优化器质量问题。

下一步为共同 RDF 输入引入版本化、源互斥的规范事实表示，同时用不同的本地元数据
映射保留 XGAP 分源访问能力。金融事实、问题、独立答案、作者代码和全局查询均保持
相同含义，旧表示及所有观察原样保留。先证明 tiny 上集合语义等价和跨源无重复规范
事实，再将新版本作为所有 RDF 方法的共同输入；不能只给其中一个方法特殊处理。
这修正的是我们的 benchmark 接线，不是对 baseline 的结果优化。
