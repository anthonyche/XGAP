# 模拟用户接入与小图内存优化验收 — 2026-09-16

本轮完成 M0 的第一版接入与 M1 的小图内存修复子阶段。它们是 research prototype
的工程验收，不是新一轮论文方法比较。历史72条NL-only结果、384条可信模板结果和
baseline均保持原样；没有运行SF0.1全量、FedShop、训练或大规模消融。

## 已实现的链路

`NL → 一次模型提议 → 显式询问模拟用户 → 收到/纠正意图 → 有界strong规划 → 一个最终计划 → 独立评分`。

新增方法 `xgap-nl-user-exact` / `xgap-nl-user-performance`，可通过普通worker/共同执行
监控入口运行。需要单独的 `--oracle-path`、`--oracle-sha256`；初始公开请求仍只有NL等
五个字段，模型输入不含私有意图、答案或物理计划。旧 `xgap-nl-strong-*` 默认行为保留。

模拟用户私有文件只允许compact逻辑查询、实体身份及题目/版本身份；gold语义可用于
离线准备该文件。`query_intent` 明确取得完整查询陈述（关系、方向、过滤、聚合等），
然后按 `entity:<var>` 逐项取得身份。也支持单独询问where/path/select等声明范围。
候选列表无正确值时返回 `none_of_these` 和正确替代值；不强迫选错。内容、作用域和
版本均检查，逐次回复在worker落盘。结构比较是精确结构比较，不做任意查询等价判定；
语义等价但写法不同也可能记为“纠正”，该标签不是NL错误率。

EXACT在受支持语义、完备oracle和预算条件下不依赖现实用户在线。测试覆盖错误过滤、
无效模型输出、空catalog、单/多实体、错误候选、过期证据、预算不足和配置缺失。
模型输出无效后仍可执行显式full-information询问；这不是隐藏的第二次模型修复。
缺少私有实体字段在模型调用前报配置问题。Oracle取得的意图可被确认，但答案质量
仍由独立评分器判断，不能用authority标记替代执行正确性。

**第一版交互策略是固定有界流程，尚未联合优化信息动作。** 两模式使用相同oracle权限
与该流程。最终strong保证以实际获得的、受支持的意图为条件；不声称对未知结构空间
已有全局strong策略、不声称全局最优。每次最多1个模型调用、1次完整意图询问、8次
实体询问、1个最终计划；执行当前题多个物理候选选实测赢家的行为仍禁止。

## 内存优化及实际证据

新的 `early-path-constraints-v1` lowering：单边时间窗口在连接前过滤；每扩展一步立即
检查严格时间递增及ACYCLIC所需的节点不等式；把已过滤的起点属性关系加入路径首个
前缀，支持模型以业务ID过滤起点。最终完整条件仍保留，方向、时间边界、重复变量、
平行边身份、contribution聚合语义不变。普通调用可显式 `optimize=True`；交互入口默认
使用该重写。旧冻结compact profile默认不切换。优化越过64算子界时回到可编译旧计划，
不会仅因可选重写而失去可行方案；语义本身不受支持时仍明确拒绝。

协调器另有两项默认修复：连接产生一行就送入原有typed去重器，省去完整原始配对
列表；计算结果bytes时逐行累计，省去完整结果JSON字符串及bytes的额外副本。
原有roots retention继续释放不再使用的中间结果。

小图重放把原8节点图增加8个无关账户和64条密集转账边；起点以业务ID过滤，参考答案
仍为同样4行。两个条件分别令噪声边在时间窗口内、窗口外。两个编译版本均执行并
与独立参考比较；这是开发期等价性/故障重放，不是运行时选计划。

|窗口内噪声例的工作量|旧lowering|新lowering|
|---|---:|---:|
|最大单算子输出行数|4,118|72|
|累计算子输出行数|6,773|1,738|
|峰值已登记结果行数|5,336|546|
|峰值已登记结果JSON bytes|3,466,190|224,277|
|源调用|14|14|

窗口外噪声例累计行数为6,493→1,162。两例均返回相同4行。
上述bytes是scheduler已登记结果的序列化大小，**不是进程RSS**，不含执行中临时空间，
也不把所有算子行数相加说成“独立数据条数”。没有据此声称远程读取减少。

另一个局部重复行压力例：120×120产生14,400个配对，最终distinct结果1行。join内部
Python分配峰值由2,891,493降至4,973 bytes；使用tracemalloc，非整个进程/数据库内存。
它验证去掉临时配对列表的效果，不代表真实FinBench均有此倍率。

## 计算界与剩余边界

令query/schema输入字节为B，H为hop界，S为source数，P为谓词数，M为生成算子数。
每个长度分支只顺序扩展，边读取总量O(SH²)，逐步无环比较总量O(H³)，局部谓词分派
O(PM)（本profile字段数有界）；节点/常规边源扫描另按输入大小计入。没有枚举物理组合。
H≤3、S≤64、M≤64，首次重写加一次旧计划fallback仍是多项式构造。
Oracle读/验证至多9次有界文件，每文件≤128KiB，query≤64KiB；无额外LLM或任意
查询等价求解。固定流程是可执行上界，不是最少澄清次数的近似比。

连接原始配对的最坏时间仍可为O(LR)，去重输出自身也可能很大；新临时空间随右侧索引
和不同输出行增长，不再额外保留所有重复配对。正确结果本身过大、低选择率、多源
大读取仍可能需要更多工作。因此尚不能宣称SF0.1四道旧OOM已经全部消除。原方法RSS
和通信guard继续存在；整批artifact存储容量隔离仍属M1后续工作，本轮未重跑大数据。

定向验收共75个不同测试通过（分批执行，重复运行不累加）：模拟用户8、路径/内存13、
旧NL边界5、共同执行6、受影响runtime/行条件/source filters/contribution43。
其间修正过测试适配的backend mapping和RDFLib并发使用；没有对baseline或历史答案调优。
真实边界只进行了上面一次模型/双后端门。

## 模拟用户如何帮助验证Performance

用户提出的方向合理：信息动作现在可运行、可计数，Performance可在风险契约允许时
少问或提前执行，EXACT付出更多信息成本以取得充分确认。下一步应测澄清次数/信息量、
模型与远程费用、总在线时间、答案质量，并保持两模式同权限。

但本地oracle本轮仅0.930ms，当前两模式询问流程相同，尚无模式收益证据。实际处理
时间与协议声明的用户等待/信息价格分开报告，不通过额外sleep或访问权限差异制造优势。
更细的询问策略、discrepancy/risk及其终止条件待下一阶段接入；用户正在推进数学契约。
