## 剩余门槛与一次批量准入

收回的 D1/D3 旧清单仍引用 8 题 pilot，不能证明最终版本 test cohort 的准入。
保留这些历史回执；不改输入/参考/估计器，不重跑 D2，不以全正确率作为就绪条件。
下一次 CPU 作业统一覆盖下面原始冻结输入，合计最多 160 次最终计划执行、零 LLM：

| Cohort | 题目数 | 目的 |
| --- | ---: | --- |
| D1 Native / RDF test | 24 / 32 | 完整 test 部署资格 |
| D3 Native / RDF test | 32 / 32 | 完整 test 部署资格 |
| D1 N/u | 28 | 实际有限候选因子的最终版本资格 |
| D1 源数 2/4/8、规模 0.25/1/4 | 6 × 2 | 每份部署的 uniform / active-anchor 固定输入 |

160 个输入已完成本地零调用规划检查，每题能选择一个物理计划；这不是服务器答案
验收。输入别名均按哈希校验，规划不读参考答案。上机先核验全部输入和计划封存，再
启动数据库。每段最多 8 题共享源会话；有类型的资源截止保留并继续未执行后缀，
不重试、不替换病例。错误答案或资源关闭不明阻止资格；所有失败保留。

准备后的配置采用节点本地 serving、方法 3 GiB / 源合计 4 GiB、单请求 60 s、
诊断 worker 120 s。源数变化时沿既有实现保持 Java 总 heap，不按源数增配资源。
本次 D1/D3 与因子源调用上限显式为 256，匹配已有 D1 F6 实测合同与旧准备清单；
D2 的已冻结 128 上限保持不变。不同数据集预算公开记录，不冒充完全相同预算。

旧准入工具把 max_calls 写死为 128，导致无法冻结匹配 F6 的新 D1 服务合同。
本次仅增加显式 `source_max_calls` 参数，默认 128 不变，并核验每段真实 observer
预算；改动不涉及 planner/compiler/estimator、baseline 逻辑或源数据。
37 项定向测试通过：旧默认、256 的逐段传递、非法上限拒绝、回执不一致停止，
以及一最终计划和现有资格检查；没有全回归或消融测试。

批量资格通过后生成对应执行清单及统一支持合同。仍需完成 21 图的实际单元绑定、
F6 同部署同预算核对与全局 API/token/墙钟/存储预算冻结，才可宣布全量可启动。
此次作业和清单生成均不启动正式五方法实验。
