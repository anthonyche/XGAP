# Strong methods in the common supervised trial boundary

2026-09-15. The common worker previously dispatched only the legacy one-shot
methods. The practical strong record route already worked, but its results could
not be handed to the common outer timing/resource/observation boundary.

Add xgap-strong-exact and xgap-strong-performance. Their input track is
trusted_template, with the practical request/profile schemas. Preserve the old
xgap-precision/xgap-performance/FedUP/FedX code paths and frozen campaign method
lists. Strong imports are lazy for those paths. Do not reinterpret a trusted
template or extra authoritative bindings as unaided open-domain NL evaluation.
The new adapter alone authorizes no campaign, population, baseline change or
large-data run; existing approved priorities remain unchanged.

The existing worker command dispatches a practical request to its ordinary record
entry once. The answer envelope points to the sealed typed answer and carries
semantic-validation, unvalidated-slot and deferred-discrepancy metadata; the full
realized query/plan/trace remain pinned through core_result. No answer reference
or oracle is read, and no answer is repaired. A faithful replay of an original
failure is still a failed method result, not successful empty output.

Model generation/repair count and input/output usage come from actual invocation
records. Missing/inconsistent usage is null, not zero. Zero new calls in an
offline replay remain zero; historical tokens do not become fresh cost. Planning,
acquisition, execution and admission timings are carried separately; unavailable
legacy frontend/grounding/compilation partitions remain null instead of invented
decompositions. The common outer timer includes worker setup, persistence, source
observation and recovery. Nested timings must not be added as disjoint stages.

run_practical_trial uses the same process guard, owned source resource monitor,
phase seal/release and failure cleanup as existing methods. It requires the
trusted-template track and exact request/profile identity. A successful live trial
must have configured_native execution provenance; an offline replay receipt is
rejected. The standalone worker also installs the caller-supplied wall deadline.
No automatic retry, method switch or alternate final execution is added.

Acceptance: six focused checks using saved response replay and controlled failure,
including a real guarded worker process that rejects an invalid binding before any
call; common live receipt rejection of replay and cleanup; old campaign method list
unchanged; unknown invocation usage preserved. One affected external admission
check verifies the baseline route still rejects preassigned SERVICE queries.
No real model/database service is needed. Native success under this combined
outer boundary remains a later deployment gate, distinct from the already verified
core native requests. This avoids replaying an unchanged paid tiny query solely
to restate core correctness.
